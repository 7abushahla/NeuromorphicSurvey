13 Hardware Execution Models

Section 12.6 closed by noting that software representation is necessary but not sufficient for a deployment claim. This section takes up the remaining question, whether a target that accepts some representation of a contract field executes it as specified. It organizes hardware by execution model rather than by vendor, because two chips from different manufacturers that both advance a barrier-synchronized global tick share more with each other, for the purposes of the deployable contract, than either shares with a chip from the same lineage built around a fundamentally different timing model. Platform examples throughout this section carry a stated generation, toolchain version, and capability status rather than a bare vendor name, and every capability record drawn from this survey's generated platform-capability data remains provisional in the sense Section 10.4 already fixes, pending full-text promotion of the underlying vendor manual. The neuron circuit that Sections 3 and 4 derive is only part of the neuromorphic engineering problem this section audits. At scale, routing, on-chip memory, and event delivery, address-event representation, network-on-chip fabrics, and multicast routing tables, cost more silicon area and energy than the neuron arithmetic itself, on Loihi's asynchronous mesh, on SpiNNaker's multicast router, and on Speck's asynchronous event fabric alike, and the family-by-family subsections below state which of these mechanisms each audited platform actually uses.

13.1 Synchronous Digital Execution

A synchronous digital system advances computation through a global or barrier-based progress signal that every core or region of the chip must reach before the next step begins, regardless of whether the circuitry beneath that signal is itself clocked uniformly. Section 4.1 already established the sharpest instance of this pattern for Intel's Loihi family. Loihi 1 and Loihi 2 compute and communicate asynchronously within a core, yet both advance a single, global algorithmic timestep across the whole chip through a barrier synchronization handshake, and IBM's TrueNorth and Tsinghua's Tianjic each advance time through their own chip-wide synchronization signal in the same structural sense . TrueNorth evaluates its entire network once per one-kilohertz global tick, encoding activation magnitude spatially across redundant, trinary-weighted neuron copies within that single tick rather than through multi-timestep temporal accumulation, a code-and-timing pairing distinct from the rate-coded correspondence Section 7 derives . SynSense's Xylo family sits in the same family from the opposite direction, a genuinely clocked, synchronous digital ASIC running an internal clock in the tens of megahertz with a fixed recurrent CuBa-LIF core and a global timestep duration configured by the host .

The mechanism this family shares is a chip-wide agreement on step boundaries, whatever happens inside one step. The semantic effect is that every layer of a mapped network advances at the same rate as every other layer within one inference, which is exactly the assumption the static per-layer horizons of Section 9.4 would need a barrier-synchronized target to relax, a demonstration Section 4.1 already states no audited source in this survey provides on physical synchronous hardware. The trade-off is that a barrier's own wall-clock duration is not fixed by the model and stretches with the slowest core's spike traffic in a given step, so a reported timestep count on this family of hardware is never automatically a fixed physical duration . The deployment consequence, developed field by field in Section 13.7, is that Loihi's own neuron dynamics field is native while its threshold and reset field on the audited route to Loihi 1 is only recoverable through the two-compartment emulation Section 12 already traces in full, a divergence that a single verdict about Loihi's synchronous execution model would not reveal.

13.2 Asynchronous Digital Execution

An asynchronous event-driven digital pipeline has no chip-wide barrier at all. A core or a processing stage advances only when an event demands it, and the chip has no shared clock signal for a barrier to be built on top of. SynSense's Speck and its predecessor core DYNAP-CNN are the confirmed instances in this survey's audited evidence, a fully asynchronous, clockless system-on-chip integrating a DVS with nine fixed convolution, integrate-and-fire, and pooling cores, reporting a single event crossing all nine layers in under four microseconds regardless of how many timesteps a software model believed it was simulating . This is Section 4.1's fourth mechanism, timestep-free event-driven execution, and it is the one mechanism in that discussion with a confirmed physical result behind it, Temporal Flexibility's deployment of a Mixed Time-step Training network to a physical Speck2e device .

The mechanism is that state updates occur strictly on event arrival, with no vector of per-layer discrete horizons for a scheduler to execute at all. The semantic effect is that a reported timestep count for a network destined for this family of hardware describes only the training-time simulation, not a quantity the chip itself schedules; Section 4.1 already states this distinction and this section does not relax it. The trade-off is that removing the barrier removes with it any single, chip-wide notion of when one inference ends and the next begins, which is why Section 12.4 records sample-duration configuration and output aggregation as host responsibilities for this family rather than native chip behavior. The deployment consequence, confirmed directly in Section 13.7's comparison table, is that Speck's time-and-termination field is recorded as host-assisted rather than native, the one point in that table where the asynchronous family's own defining property, no chip-wide tick, produces a different status than the barrier-synchronized family's native time-and-termination field, even though both families ultimately depend on a host to declare when a result should be read.

13.3 Software-Programmable Many-Core Systems

A software-programmable many-core system executes a user-supplied program on each of many general-purpose or near-general-purpose cores rather than realizing one fixed neuron circuit in hardware. SpiNNaker 1 and SpiNNaker 2 are this survey's confirmed instances, an ARM-core-based digital many-core architecture that simulates arbitrary software-defined neuron models rather than one built-in dynamical primitive, at a default software convention near one millisecond per tick that Section 3.6 already identifies as a scheduling convention rather than a hardware limit . This is also the family in which Table 5's CUBA-LIF row places sPyNNaker's own documented default cell type, IF_curr_exp, a current-based synapse paired with an exponentially decaying current rather than the instantaneous sum IF and LIF assume .

The mechanism is that neuron and synapse behavior is compiled C code running on a general-purpose core rather than a fixed circuit, so this family's capability status for a given contract field tracks what a user is willing to implement rather than what the silicon fixes in place. The semantic effect is direct for the reset-and-threshold field. SpiNNaker's built-in cell types use PyNN-conventional hard-reset semantics by default, and reset by subtraction is achievable only by writing a bespoke C neuron model with a custom spike-detection callback, not by selecting a built-in option, which is why Section 12 records the SNN Toolbox to sPyNNaker route's threshold-and-reset field as unsupported for the audited default configuration even though the route as a whole reaches physical silicon . The trade-off is a place-and-route resource budget rather than a silicon-area one; SpiNNTools compresses multicast routing tables toward a roughly 1024-entry-per-chip router budget and partitions the application graph at close to 256 atoms per core given per-core memory limits, a mapping constraint distinct from anything a barrier-synchronized or fully asynchronous chip needs to satisfy . The deployment consequence is that this family's programmability makes an absolute claim about what it cannot do particularly risky. A capability recorded as unsupported for this family describes the audited default configuration and toolchain, not a hardware ceiling a custom kernel could not in principle raise.

13.4 Analog and Mixed-Signal Execution

An analog or mixed-signal system realizes neuron and synapse dynamics as physical circuit behavior evolving in continuous time, typically at a fixed acceleration factor relative to biological or wall-clock time, rather than as a discrete-time numerical recurrence. Heidelberg's BrainScaleS-1 and BrainScaleS-2 are the confirmed instances developed in depth in this survey's audited evidence, wafer-scale and single-chip analog systems physically emulating adaptive-exponential or leaky-integrate-and-fire circuits at roughly one thousand to ten thousand times accelerated analog time, requiring per-neuron calibration to correct manufacturing mismatch before a mapped network reaches usable accuracy . SynSense's DYNAP-SE2 and Innatera's Pulsar extend the same execution family to smaller, commercially oriented mixed-signal parts; this survey's audited evidence located no rate-coded ANN-to-SNN conversion pipeline for DYNAP-SE2, and every quantitative performance figure it located for Innatera Pulsar is vendor-sourced without an independent peer-reviewed benchmark, a gap this survey states rather than resolves .

The mechanism is that threshold crossing and reset are properties of a physical neuron circuit rather than a digital comparison against a stored number, so the threshold-and-reset field is native by construction on hardware in this family, exactly the status Section 13.7's comparison table records for BrainScaleS-2. The semantic effect is that numeric precision is not a bit width chosen by a compiler but a resolution set by circuit mismatch and calibration quality, which is why the same table records BrainScaleS-2's precision field as transformed rather than native, a mismatch-and-calibration process standing in for what a digital platform would call quantization. A caution belongs here, not deferred to a later section, because the audited physical route for hxtorch, the PyTorch interface to BrainScaleS-2, targets its non-spiking hagen mode, executing analog matrix multiplication directly rather than the spiking, leaky-integrate-and-fire hxtorch.snn mode . This survey's own source notes this distinction explicitly, and the physical latency and energy measurement Stradmann et al. report for a mobile electrocardiogram application must not be read as a measurement of the spiking execution of hxtorch.snn . The separate hardware-in-the-loop evidence for BrainScaleS-2's own spiking mode, hxtorch.snn's injection of measured membrane traces into automatic differentiation for the Yin-Yang classification task, is Section 6.3's E2 result, a genuinely spiking, genuinely physical claim, but a distinct one from the non-spiking route this section's platform-capability comparison audits . The trade-off for the whole family is that accelerated time is a design feature for some workloads and a representational obstacle for others; a network trained assuming discrete algorithmic steps must be re-expressed against continuous circuit dynamics before either the timing or the precision fields can be evaluated as this survey's contract requires.

13.5 FPGA and Custom-ASIC Implementations

An FPGA or custom-ASIC implementation realizes a fixed or reconfigurable digital circuit purpose-built for one execution model rather than adapting a general-purpose many-core architecture or a continuous analog substrate to the task. BrainChip's Akida family is this survey's most thoroughly audited instance, a commercial neuromorphic system-on-chip whose standard QuantizeML-to-CNN2SNN deployment route collapses the multi-step firing-rate window the classical correspondence assumes into a single feedforward pass (Section 9.6, Section 14.3). UCLouvain's MorphIC is the clearest controlled same-silicon comparison available in this survey's audited evidence between two neural codes, reporting rate coding reaching 97.8 percent accuracy at 205 microjoules per classification against rank order coding reaching 95.9 percent accuracy at 21.8 microjoules per classification on the identical MNIST task and chip, a result Section 4.3 already develops in full . A broader FPGA family, including Cerebron, SyncNN, and other accelerators surveyed for their code-fidelity properties in earlier sections, implements the classical IF-plus-reset-by-subtraction-plus-rate-coding pipeline with varying fidelity per design; SyncNN and a subset of these designs expose reset by subtraction as an explicit, user-selectable configuration, while others do not document their reset polarity at all .

The mechanism this family shares is that the execution model is fixed into the circuit at design time rather than negotiated by a general-purpose core's software or a continuous physical process. The semantic effect is that a custom ASIC or a synthesized FPGA design can realize almost any of the neuron models Section 3.3 derives natively, at the cost of committing that choice before fabrication or synthesis rather than after. The trade-off is exactly the one Section 9.6 and Section 9.7 already establish for Akida specifically. Every confirmed instance in this survey's audited corpus of a conversion method reaching physical silicon through this family abandons the classical rate-coded correspondence for a code native to the target rather than adapting the target to carry an unmodified rate code. The deployment consequence is that a capability status reported for this family is a statement about one fabricated or synthesized design, not about what a different FPGA bitstream or a different ASIC tapeout targeting the same neuron family could in principle achieve; Section 9.4's APEX and NeuroFlex accelerator models, synthesized in RTL rather than fabricated, are E4 hardware-model evidence for exactly this reason, a documented design rather than a measured chip.

13.6 Conventional Processors and Emerging Devices

A conventional processor executing an SNN workload is a general-purpose CPU or GPU running a simulator rather than any dedicated spiking substrate, and it is, by a wide margin, the execution model behind the majority of the evidence this survey classifies as E5 throughout Sections 7 through 9. mlGeNN's own GPU-only deep-CNN conversion results, reaching close to matched accuracy between a converted VGG-16 and its ANN baseline on ImageNet, are a direct instance, useful evidence about the classical correspondence's numerical behavior at scale and not evidence about any neuromorphic target at all . BIDL's multi-backend design, compiling through Lyngor to either the Lynxi KA200 many-core, compute-in-memory chip or a conventional CPU or GPU fallback, makes the same processor a documented option inside one vendor's own toolchain rather than only an implicit default outside every dedicated toolchain .

IBM's NorthPole belongs in this family for a reason worth stating precisely rather than assuming from its lineage. NorthPole is IBM's own described successor to TrueNorth, but it is a purely digital, low-precision matrix-multiply accelerator with no spiking or event-driven neuron model and no membrane-potential dynamics; its reported efficiency derives from memory locality and low-bit multiply-accumulate execution, not from event-driven temporal sparsity of the kind this survey's deployable contract is built to describe . NorthPole is therefore outside the eleven-field contract's intended scope in the same sense a conventional accelerator is, and naming it a neuromorphic chip on the strength of its lineage alone would be exactly the kind of vendor-name-driven overclaim Section 2.4 already warns against.

In-memory and emerging-device systems are covered here only to deployment-relevant depth, consistent with the referral Section 2.6 already gives to the underlying device physics. Lynxi's KA200, a compute-in-memory, many-core, heterogeneous-fusion chip built on the Tianjic lineage and natively supporting both deep-learning ANNs and spiking networks with mixed-precision compute, is this survey's clearest confirmed instance, and its own access limitation, a deployment path effectively unavailable outside mainland China per the sources reviewed, is itself a deployment-relevant fact rather than a detail this survey sets aside . The present discussion stops after this deployment-relevant depth. For the underlying device-level physics of brain-inspired and analog or emerging-device neuromorphic substrates, see Zolfagharinejad et al. , already referred to at the same boundary in Section 2.6.

Three columns of Table 23 carry the same status at every one of the nine platforms, and the uniformity is itself a finding rather than a coincidence of these nine choices. Graph operators are transformed everywhere, no audited platform accepts an arbitrary computation graph without a mapper restructuring, splitting, or rejecting unsupported topology first. Encoder-decoder and host-operations fields are host-assisted everywhere, confirming at scale the boundary Section 12.4 already states, that no platform audited in this survey performs both input encoding and output decoding entirely on-chip. Neuron dynamics is native everywhere in this table, yet Table 5 already shows that a native neuron-dynamics status can still require a multi-compartment emulation for one specific mechanism inside it, adaptive threshold behavior or subtractive reset on Loihi being the confirmed case, so a coarse field's uniform status does not certify a finer field nested inside it.

Threshold and reset is the field with the widest spread of statuses in Table 23, the single field this survey has traced in the greatest depth across Section 3.5, Section 8.3, and Section 12's typed edge schema. Plasticity and state persistence is the second most heterogeneous field, the same native-capability-versus-exercised-route gap Table 11 documents for on-chip learning. Reading a platform's row in isolation, without checking which fields the specific audited route actually exercises, risks exactly the overclaim this survey's capability vocabulary exists to prevent.

A platform's contract-field status, however complete, describes what that platform can do in principle for one audited configuration. It does not, on its own, establish that a specific published network traveled the complete chain from a training framework to that platform without breaking at an intermediate edge. Section 14 closes that gap, tracing seven named candidate routes edge by edge through exactly the software boundaries Section 12 types and exactly the hardware families this section compares, and assigning each one a single validated route state rather than inferring it from how compatible the endpoints look on paper.
