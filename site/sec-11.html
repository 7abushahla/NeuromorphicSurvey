11 Software, Interchange, and Compilation

Section 10.4 established that a contract field's representability must be checked before its execution is asked about at all. This section checks it, following the software path a network travels in the order it is actually traveled, a training or simulation framework, serialization or export, an intermediate representation where one is used, compiler lowering and mapping, a runtime, and the host input and output work that surrounds every stage. Every edge in that path is typed using the schema Table 18 fixes below, input, output, preserved, transformed, rejected, and evidence, so that a claim about one boundary is never confused with a claim about a different one.

11.1 The Framework Boundary

The sixteen training and simulation frameworks this survey's audited evidence covers do not form one category. They divide by what representation they commit to at the point a network is defined and by which hardware family, if any, their own maintainers built them to reach. Grouping by this commitment, rather than listing sixteen names in alphabetical or chronological order, is what lets the rest of this section state which boundary a given framework's output must cross next.

A first group trains a network natively in PyTorch and commits to a spiking representation from the first line of model code. SpikingJelly, snnTorch, and Norse all expose PyTorch-native spiking layers trained by the surrogate-gradient or exact spike-time methods of Section 6, and all three differ in their default reset rule at the point of definition, exactly the divergence Section 3.4 already traces for SpikingJelly. snnTorch's snn.Leaky defaults to a subtractive reset, matching SpikingJelly's own converted-network default, while Norse's LIFCell and LIFRecurrentCell default to reset-to-zero . Neither snnTorch nor Norse has a first-party path to a specific physical target audited in this survey; Norse instead exports to NIR, with its own documentation stating a caveat that a round-trip export and import can produce a different spike pattern on identical input, a framework-level instance of the representation risk this section develops in full . This group's frameworks are therefore evaluated by this survey chiefly as sources of the reset-semantics divergence itself, not as members of an audited hardware route.

A second group descends from biological point-neuron simulation rather than from a PyTorch training loop. Brian2 and NEST are differential-equation and point-neuron simulators whose native application is large-scale biological modeling rather than deep-network conversion; each reaches a converted convolutional network only through SNN Toolbox acting as an external output backend, not through its own native import path . Nengo instead implements the Neural Engineering Framework, analytically solving decoding weights over spiking tuning curves rather than training by backpropagated error, a construction distinct enough from the rate-matching correspondence of Section 7.2 that its NengoDL bridge and ReLU-to-spiking converter should not be read as an instance of the same theorem . PyNN sits above several of these simulators as a shared front end, letting one described model target NEST, BrainScaleS-2, or SpiNNaker without being rewritten per backend, though sPyNNaker, PyNN's own SpiNNaker-specific implementation, is the concrete backend this survey's audited routes actually exercise rather than the generic PyNN interface itself .

A third group is a vendor toolchain built around one hardware family from the outset. Lava and Lava-DL target Loihi 2, Sinabs targets SynSense's DYNAP-CNN and Speck family, Rockpool targets SynSense's Xylo family, QuantizeML targets BrainChip's Akida family, hxtorch targets BrainScaleS-2, and BIDL targets Lynxi's KA200 lineage . Because each of these frameworks is co-designed with its one target, the framework-boundary edge for this group is typically the smallest source of divergence in the entire chain; Section 11.5 shows the larger transformations for this group happen one or two edges downstream, at the mapper or the runtime rather than at model definition. mlGeNN occupies a narrower version of the conversion-specific role SNN Toolbox occupies more broadly, adding explicit deep-CNN conversion support to the GPU code-generation library GeNN and reporting large-scale conversion results at ImageNet scale, but as GPU simulation only, without a documented route to neuromorphic silicon audited in this survey .

SNN Toolbox is the fourth group's sole confirmed member in this survey's audited evidence, a conversion-specific tool whose entire purpose is producing a rate-coded, reset-by-subtraction IF network from a Keras, PyTorch, Caffe, or Lasagne source model and routing that network toward one of several output backends, NxTF, sPyNNaker, Brian2, or Cerebron among them . Section 13.2 traces two of these output paths to physical silicon in full.

11.2 Serialization and the Intermediate Representation

Serialization turns a framework's in-memory graph into a file or object another program can consume. Most vendor toolchains in this survey's audited evidence serialize into a format specific to that vendor's own downstream mapper, Sinabs's internal DynapcnnLayer representation and Lava-DL's HDF5 network-exchange schema being two audited instances . NIR is the one cross-vendor exception this survey's audited evidence covers in depth, an interchange format that multiple frameworks, SpikingJelly, Sinabs, Rockpool, and Norse among them, can both write to and read from, aiming to let one trained network reach several otherwise unrelated backends through a single schema rather than a bespoke pairwise exporter for every framework-to-framework combination .

NIR's own documentation states directly that its primitives are idealized and that the schema does not constrain a backend's integration order, spike timing, reset timing, or numerical quantization, so accepting a NIR graph never by itself establishes that two different backends execute it identically . Section 3.4 already gives the sharpest instance of this idealization becoming a representational limit rather than a merely stylistic one. NIR 1.0.8's IF, LIF, and CubaLIF primitives encode only a fixed-value post-spike reset, and a missing or null reset value is materialized as reset-to-zero, so a schema that has no field for reset by subtraction cannot silently misrepresent it. It rejects it structurally, at the level of what the format is capable of expressing at all . This is a property of NIR 1.0.8 specifically, introduced into the schema in 2025, so a source describing an earlier version of the format should not be read as describing the same reset contract .

11.3 Export, Compilation, and Mapping

Compilation and mapping are where a network's graph is lowered toward a specific target's operator set, partitioned across cores or processing elements, and placed and routed within that target's physical resource budget. This is also where this survey's audited evidence is richest and most precisely typed, because the same reset-semantics question Section 3.4 raises for one platform recurs, with a different answer each time, across eleven separately audited edges spanning SpikingJelly, Sinabs, NIR, Lava, Lava-DL, NxTF, and two physical targets. Two edges are absent from every row of Table 18, and their absence is itself informative rather than an omission. No audited source in this survey documents a route from Lava or NetX's own soft-reset intent to a custom Loihi 2 neuron process outside the public Lava and NetX artifacts; Loihi 2's neuron engine is documented as fully microcode-programmable, which makes an inference of impossibility unwarranted, and this survey records the edge as undocumented for exactly that reason rather than omitting it . Compilation and mapping edges outside the reset-semantics chain follow the same schema with different subject matter. SNN Toolbox's bridge into NxTF folds batch normalization, applies percentile-based weight and threshold normalization, and preserves the reset-by-subtraction default at the point of compilation, but its own boundary notes state plainly that NxTF is Keras-native, so a PyTorch-trained SpikingJelly model has no generic bridge into this specific compiler regardless of what its own reset rule is . QuantizeML's uniform, symmetric integer quantization is consumed directly by CNN2SNN's mapper, which folds batch normalization and activation quantization into a per-neuron static threshold computed once at conversion time, a transformation this survey records in full in Section 9.6 and revisits as a named route in Section 13.2 .

11.4 Runtime Scheduling and Host Input and Output

A runtime is the software layer that actually executes a compiled graph on a target, whether that target is physical silicon or a CPU-based simulation standing in for it. NxSDK is Loihi 1's register-level runtime, superseded for Loihi 2 by the Lava runtime's Magma layer, whose Loihi-targeting components remain proprietary and gated to members of Intel's Neuromorphic Research Community . samna is SynSense's cross-chip developer interface, applying a configuration object to physical Speck or DYNAP-CNN silicon and streaming event data through a chain of source, filter, and sink nodes . SpiNNaker's runtime splits across the on-chip SpiN1API operating system and the host-side SpiNNTools pipeline that loads per-core parameter blocks, signals synchronized execution start across every core, and reads results back through the PyNN API after the run completes . In every one of these cases, the runtime that executes the graph and the host process that prepares its input and reads its output are two different pieces of software crossing a boundary that the deployable contract's host-operations field, fixed in Section 10.2, exists to make explicit.

That boundary is not a peripheral detail this survey's audited evidence lets a platform avoid. Every reviewed digital platform still depends on a host-side step that converts an input into the target's native event or packet format before injection and converts output spikes or counters back into a readable result once execution finishes. Rockpool's Xylo mapper illustrates the same boundary from the accelerated-simulation side of a runtime rather than the physical side, deploying through either XyloSamna or XyloMonitor in accelerated-time or real-time streaming mode, with on-chip power recorded by current monitors sampled at 1280 hertz, while parameter quantization, sample-duration configuration, and application-level decoding all remain the host's responsibility rather than the chip's . This is the concrete instance behind the host-operations status recorded uniformly across every platform in Section 12.7's comparison table, and it is also a direct consequence of the boundary Section 2.3 already drew between an event-driven execution model and an end-to-end event-driven system. A platform whose neuron cores execute without a shared clock can still depend on a host that is neither event-driven nor spiking to prepare its input and interpret its output, and no platform audited in this survey removes that dependency entirely.

11.5 What Transforms, What Is Rejected

Reading Table 18 as a whole rather than edge by edge surfaces three patterns that recur across the software stack independent of which vendor built which piece of it.

The first pattern is that reset semantics are transformed or rejected far more often than they are preserved natively. Of the nine typed compilation edges in Table 18, two reject the source model outright, three transform the reset rule into a different one, one is undocumented, and only three preserve subtractive reset, one of them, NxTF's route to Loihi 1, only through an emulation that doubles compartment allocation. No audited edge in this survey's evidence base preserves subtractive reset through a native, unmodified, single-compartment hardware primitive on a chip whose own default reset behavior is reset-to-zero. Norse's own documented reset-to-zero default and its separately documented round-trip NIR re-import discrepancy extend this same pattern one layer further back, into a framework's export and import of its own graphs rather than only its export toward a different framework .

The second pattern is that numeric precision is quantized at nearly every boundary this survey's audited evidence documents, and the specific bit widths chosen differ from edge to edge rather than converging on one industry default. NxTF's soft-reset workaround preserves 9-bit weight precision on Loihi 1. Sinabs's mapper quantizes to 8-bit weights and 16-bit membrane state for Speck. SpiNNaker2's NIR importer preserves 8-bit weights alongside 32-bit floating-point state. QuantizeML's uniform symmetric integer quantization for Akida commonly uses one, two, four, or eight bits depending on the layer and the configured precision . A precision field stated as bits alone, without naming which of weights, thresholds, or state that count applies to, is therefore an incomplete report against the contract fixed in Section 10.2.

The third pattern is that maintenance status and access conditions are themselves facts about a software boundary, not a footnote outside the contract. Intel archived the entire Lava, Lava-DL, and NetX stack in 2026, stating that all Lava repositories are archived with no successor software development kit yet announced, which freezes every edge in Table 18 that terminates at Loihi 2 through that stack at whatever state it held at the point of archival . Loihi access more generally remains gated to members of Intel's Neuromorphic Research Community rather than openly available . Lynxi's BIDL, Lyngor, and LynSDK toolchain is documented in the sources this survey reviewed as effectively unavailable outside mainland China . A route that is otherwise exact or physical by every other test in this section can still fail a practitioner who cannot obtain the access it requires, a distinction Section 17 returns to as an open problem rather than resolving it here.

11.6 Referrals to Software and Interoperability Surveys

The present discussion stops after typing the specific compilation and runtime edges this survey's audited evidence supports, organized around the reset-semantics case because it is the field with the deepest cross-toolchain evidence available. For a broader inventory of SNN training and simulation frameworks compared from a data-science perspective, see Manna et al. , which is particularly useful for comparing usability and API design across nine frameworks this section did not evaluate on those terms. For an extension of the software-implementation view to GPU and RISC-V accelerators and a discussion of incompatible reporting practices across that wider set of targets, see Farsa et al. . For NIR's own account of the semantic disagreements it was built to expose across simulators and hardware back ends, beyond the reset-specific case developed here, see Pedersen et al. , whose original comparison motivates the schema this section applies.

Software representation is necessary but not sufficient for a deployment claim. An edge can be native, physical, and E1 evidenced, and still say nothing about what happens once the represented network reaches silicon built on a fundamentally different execution model than the barrier-synchronized, digital, many-core assumption implicit in much of this section's evidence. Section 12 takes up that execution question directly, organizing hardware by how it advances time and computation rather than by vendor, and comparing platforms through the same eleven-field contract this section has already begun to apply.
